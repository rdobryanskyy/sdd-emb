# Machine Embroidery File Formats

> Compiled through web research on 2026-07. Before you use a number from this file as a hard constraint in code (for example, a database CHECK constraint), compare it with the authoritative manufacturer or format specifications.

This document is reference material for the sdd-emb pipeline (data-model, api, and the embroidery-digitize/optimize/export/qa skill family). It gives a summary of the file formats that a digitizing or production pipeline will probably read, write or validate against.

The best ground-truth sources for the byte-level layout are the open-source parser projects. Their authors made them through reverse engineering of real files. A community that finds edge cases in production keeps them up to date:

- **pyembroidery** (Python) — [GitHub: EmbroidePy/pyembroidery](https://github.com/EmbroidePy/pyembroidery), [PyPI](https://pypi.org/project/pyembroidery/)
- **libembroidery** (C) — [GitHub: Embroidermodder/libembroidery](https://github.com/Embroidermodder/libembroidery), part of the [Embroidermodder](https://github.com/Embroidermodder) project
- **Ink/Stitch** (Inkscape extension, with logic similar to pyembroidery) — [File Formats docs](https://inkstitch.org/docs/file-formats/)
- **EduTechWiki "Embroidery format" series** — an academic wiki that has existed for a long time, with a technical page for each format, e.g. [Embroidery format DST](https://edutechwiki.unige.ch/en/Embroidery_format_DST), [...EXP](https://edutechwiki.unige.ch/en/Embroidery_format_EXP), [...JEF](https://edutechwiki.unige.ch/en/Embroidery_format_JEF), [...PES](https://edutechwiki.unige.ch/en/Embroidery_format_PES), [...HUS](https://edutechwiki.unige.ch/en/Embroidery_format_HUS)
- **libpes wiki** (reverse-engineering notes for Brother PES/PEC) — [PES format](https://github.com/frno7/libpes/wiki/PES-format)
- **KDE Community Wiki** — [Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format)

The internal unit convention of pyembroidery is a good concept to use again in a data model. It normalizes each format to **1/10 mm per unit**, with +Y down (the screen and graphics convention). It flips the axis at the read and write boundaries, as each format needs [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery). Its core command vocabulary is `STITCH`, `JUMP`, `TRIM`, `STOP`, `END`, `COLOR_CHANGE`, `NEEDLE_SET`, `SEQUIN_MODE`, `SEQUIN_EJECT` (and `SLOW`/`FAST` for the Barudan `.u01` format). This is a good canonical command set for a model, because its authors designed it as a superset for about 40 formats [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).

## DST (Tajima) — detail

- The structure has two parts: a **512-byte header** (only ~125 bytes contain metadata; the remaining bytes are padding), then the body with the stitch data [Source: EduTechWiki DST + aggregated search](https://edutechwiki.unige.ch/en/Embroidery_format_DST).
- Stitch commands are **always 3 bytes** long. One record contains the X/Y displacement and a command flag [Source: search-aggregated pyembroidery/EduTechWiki summary].
- Coordinates are **relative** (the delta from the previous needle position), not absolute.
- The command set that the pyembroidery project and its community agreed on: `STITCH`, `JUMP`, `TRIM`, `STOP`, `END`, `COLOR_CHANGE`, `SEQUIN_MODE`, `SEQUIN_EJECT` [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).
  - `JUMP` = a move without a needle strike (`block_needle_bar`); `STITCH` = a move and a needle strike.
  - `STOP` and `COLOR_CHANGE` are frequently the **same command**. Machines know the difference between "pause" and "change thread" from the color-change target: a different needle or color slot, or the same one.
  - In classic DST, a `TRIM` usually comes from a sequence of consecutive `JUMP`s (frequently after 3, sometimes up to 5 jumps). It is not a separate explicit byte pattern [Source: search-aggregated pyembroidery documentation summary].
- **Hard format limit**: the classic maximum delta of one stitch (or one jump) is **121 units of 0.1 mm = 12.1 mm**. The reason is that DST used a ternary coding system that came from punch tape. A longer move must be divided into more than one jump command [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery), confirmed by [Wilcom EmbroideryStudio docs — Stitch & jump length settings](https://docs.wilcom.com/embroiderystudio/26/en/OnlineHelp/Setup/machines/Stitch_jump_length_settings.htm) ("ternary coding system: 12.1 mm — e.g. Tajima machines").
- DST **does not keep thread or color names or RGB values**. It keeps only color-change *markers* in sequence. The operator, or a companion `.COL`/`.INF`/`.EDR` sidecar file (as pyembroidery uses), must supply the actual color for each marker [Source: search-aggregated DST summaries; pyembroidery README lists `.col`, `.edr`, `.inf` as "related formats"](https://github.com/EmbroidePy/pyembroidery).
- Native **sequin support**: DST is the one format that pyembroidery treats as fully sequin-capable. A `SEQUIN_MODE` toggle changes the interpretation of the next `JUMP`s into `SEQUIN_EJECT`s at the jump destination [Source: pyembroidery README / issue discussion](https://github.com/EmbroidePy/pyembroidery).

## EXP (Melco) — detail

- **No header** — the file contains only stitch data [Source: search-aggregated EXP summaries, e.g. StitchPilot EXP guide](https://stitchpilot.ai/formats/exp).
- Coordinates are **relative** to the previous point. They are encoded as signed (2's complement) 8-bit bytes for X and Y. This gives a range of -127..127 for each axis in 0.1 mm units, thus a **hard maximum delta of one stitch of ~12.7 mm**. This agrees with the documented value of Wilcom: "binary coding system: 12.7 mm — e.g. Barudan machines" [Source: Wilcom Stitch & jump length settings](https://docs.wilcom.com/embroiderystudio/26/en/OnlineHelp/Setup/machines/Stitch_jump_length_settings.htm).
- The classic EXP from Melco has **no standardized color palette block**. The thread order and the color intent must be recorded and documented outside the file. Some sources say that EXP variants from Bernina contain basic color-scheme information. This is not a universal guarantee for all EXP producers [Source: search-aggregated EXP summaries].

## JEF / JEF+ (Janome) — detail

- File layout (from a byte-level reverse-engineering document): **116-byte file header** → thread-color list → thread-type list → [JEF+ plus-header] → stitch list → {JEF+ plus-detail, JEF+ only} [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- The documented header fields are: stitch offset (bytes 0–3, little-endian), date `YYYYMMDD` (bytes 8–15), time `HHMMSSxx` (bytes 16–23), thread/color-change count (24–27), stitch count (28–31), a **hoop code** (32–35, values 0–4 for specific hoop sizes), and five sets of extent (bounding box) measurements in 0.1 mm units (36–112) [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- Thread colors refer to a **fixed built-in palette of 78 entries**. Each entry is a 4-byte code for an RGB value and a standard name [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- Stitches: signed 8-bit X/Y displacement bytes, range -127..127, 0.1 mm units. The byte `0x80` is reserved as an **escape code**. `0x80`, then a command byte (and for most commands two more displacement bytes), starts a color change (code 1), a move instruction (code 2), or the end of the design (code 16). The end of the design is the 2-byte sequence `0x80 0x10`, not the general 4-byte pattern [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- Because of the hoop-size field in the header, a JEF file can natively state "this design needs at least hoop size N". A validating pipeline can compare this with the hoop inventory of a target machine before dispatch [Source: Janome — Saving Files for Janome Embroidery Machines](https://www.janome.com.au/saving-files-for-janome-embroidery-machines/).

## VP3 (Husqvarna Viking / Pfaff) — detail

- Vendors (not an independent specification) describe it as a block-structured format: file header (design name, stitch count, dimensions), thread color info, stitch data and machine instructions, hoop position and layout data, and an embedded preview image [Source: aggregated vendor descriptions, e.g. embdesigntube VP3 guide](https://embdesigntube.com/en-gb/blog/vp3-embroidery-files-husqvarna-format-guide).
- Vendor marketing frequently calls it "vector-based". This implies that it keeps more structure than a flat list of relative stitch deltas. But this research pass found no independent byte-level specification from reverse engineering. Use the "vector" description as a design or marketing claim, not as a verified bit layout <!-- TBD: verify — no independent byte-level VP3 spec found -->.
- pyembroidery reads and writes `.vp3`. This is the most reliable practical confirmation that its structure is sufficiently known for production tooling [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).

## HUS (Husqvarna Viking, legacy) — detail

- It is older than VP3. It was in use through the 1990s [Source: aggregated search, e.g. emblibrary Husqvarna formats help](https://www.emblibrary.com/EL/help.aspx?page=helpformathusqvarna).
- It uses a **proprietary compression of the LZSS family** (licensed technology related to the ARJ compressor). This is a major reason why it is one of the legacy formats that open tooling cannot easily round-trip [Source: aggregated search results citing Greenleaf/ARJ lineage; see also Just Solve the File Format Problem: HUS](http://justsolve.archiveteam.org/wiki/HUS).
- The first 4 bytes of a file are one of a small set of fixed magic numbers (`5BAFC800`, `5BFFC800` or `5DFCC800`) [Source: aggregated search results, cross-referenced against Just Solve the File Format Problem: HUS](http://justsolve.archiveteam.org/wiki/HUS).
- pyembroidery lists `.hus` as **read-only**. Thus its authors do not think that it is safe or complete enough to write [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).

## PES / PEC (Brother) — detail

- A `.pes` file is a **two-layer container**: an outer PES section for the PE-Design authoring software of Brother, and a nested **PEC block** that the physical embroidery machine actually uses (design name, color list, machine commands, low-resolution stitch graphic) [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).
- Versioned: the observed headers go from `#PES0001` to at least `#PES0060`. **The header layout is different for each version.** Thus a parser must examine the version string before it trusts the field offsets [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).
- The color handling changed between generations: **PES v1–v4 use a fixed, predefined PEC palette of 64 threads** (the file refers to colors only by index). **PES v5/v6 replace this with configurable/custom thread definitions** [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).
- V4–V6 (and later) add an **addendum block** after the classic PEC graphics block, with ~0x90 (144) bytes of more metadata for each color [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).

## Sequins in newer formats

DST is the only format that the pyembroidery project treats as natively and fully sequin-capable (`SEQUIN_MODE` / `SEQUIN_EJECT`). For other formats, the encoder uses a configurable "sequin contingency" as a fallback. It changes a sequin instruction into a `JUMP` or a `STITCH`, removes it, or uses a format-specific "utilize" behavior [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery). Tajima introduced the first commercial sequin embroidery machine in 1986 [Source: Wikipedia — Machine embroidery](https://en.wikipedia.org/wiki/Machine_embroidery).
