# Machine Embroidery File Formats

> Compiled via web research on 2026-07 — verify against authoritative manufacturer/format specs before treating any number here as a hard constraint in code (e.g. a database CHECK constraint).

This document is reference material for the sdd-emb pipeline (data-model, api, and the embroidery-digitize/optimize/export/qa skill family). It summarizes the file formats a digitizing/production pipeline is likely to read, write, or validate against.

The single best ground-truth sources for byte-level layout are the open-source parser projects, because they were built by reverse-engineering real files and are kept in sync by a community that hits edge cases in production:

- **pyembroidery** (Python) — [GitHub: EmbroidePy/pyembroidery](https://github.com/EmbroidePy/pyembroidery), [PyPI](https://pypi.org/project/pyembroidery/)
- **libembroidery** (C) — [GitHub: Embroidermodder/libembroidery](https://github.com/Embroidermodder/libembroidery), part of the [Embroidermodder](https://github.com/Embroidermodder) project
- **Ink/Stitch** (Inkscape extension, wraps pyembroidery-like logic) — [File Formats docs](https://inkstitch.org/docs/file-formats/)
- **EduTechWiki "Embroidery format" series** — a long-running academic wiki with per-format technical pages, e.g. [Embroidery format DST](https://edutechwiki.unige.ch/en/Embroidery_format_DST), [...EXP](https://edutechwiki.unige.ch/en/Embroidery_format_EXP), [...JEF](https://edutechwiki.unige.ch/en/Embroidery_format_JEF), [...PES](https://edutechwiki.unige.ch/en/Embroidery_format_PES), [...HUS](https://edutechwiki.unige.ch/en/Embroidery_format_HUS)
- **libpes wiki** (Brother PES/PEC reverse-engineering notes) — [PES format](https://github.com/frno7/libpes/wiki/PES-format)
- **KDE Community Wiki** — [Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format)

pyembroidery's internal unit convention is worth reusing conceptually in a data model: it normalizes every format to **1/10 mm per unit**, with +Y pointing down (screen/graphics convention), flipping the axis at read/write boundaries per format [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery). Its core command vocabulary — `STITCH`, `JUMP`, `TRIM`, `STOP`, `END`, `COLOR_CHANGE`, `NEEDLE_SET`, `SEQUIN_MODE`, `SEQUIN_EJECT` (plus `SLOW`/`FAST` for the Barudan `.u01` format) — is a reasonable canonical command set to model against, since it was designed specifically to be a superset covering ~40 formats [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).

## DST (Tajima) — detail

- Two-part structure: a **512-byte header** (only ~125 bytes actually populated with metadata; the rest is padding) followed by the stitch-data body [Source: EduTechWiki DST + aggregated search](https://edutechwiki.unige.ch/en/Embroidery_format_DST).
- Stitch commands are **always 3 bytes** long, encoding X/Y displacement plus a command flag in the same record [Source: search-aggregated pyembroidery/EduTechWiki summary].
- Coordinates are **relative** (delta from the previous needle position), not absolute.
- Mandated/community-agreed command set per the pyembroidery project: `STITCH`, `JUMP`, `TRIM`, `STOP`, `END`, `COLOR_CHANGE`, `SEQUIN_MODE`, `SEQUIN_EJECT` [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).
  - `JUMP` = move without a needle strike (`block_needle_bar`); `STITCH` = move + needle strike.
  - `STOP` and `COLOR_CHANGE` are frequently the **same underlying command** — machines distinguish "pause" from "change thread" by whether the color-change target is a different needle/color slot or the same one.
  - A `TRIM` is conventionally inferred from a run of consecutive `JUMP`s (commonly after 3, sometimes up to 5 jumps in a row) rather than being its own explicit byte pattern in classic DST [Source: search-aggregated pyembroidery documentation summary].
- **Hard format limit**: the classic maximum single-stitch (or single-jump) delta is **121 units of 0.1 mm = 12.1 mm**, because DST historically used a ternary punch-tape-derived coding system; anything longer must be split into multiple jump commands [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery), corroborated by [Wilcom EmbroideryStudio docs — Stitch & jump length settings](https://docs.wilcom.com/embroiderystudio/26/en/OnlineHelp/Setup/machines/Stitch_jump_length_settings.htm) ("ternary coding system: 12.1 mm — e.g. Tajima machines").
- DST **does not store thread/color names or RGB values** — only color-change *markers* in sequence; the actual color assigned to each marker is a convention the operator or a companion `.COL`/`.INF`/`.EDR` sidecar file (as used by pyembroidery) must supply [Source: search-aggregated DST summaries; pyembroidery README lists `.col`, `.edr`, `.inf` as "related formats"](https://github.com/EmbroidePy/pyembroidery).
- Native **sequin support**: DST is the one format pyembroidery treats as fully sequin-capable — a `SEQUIN_MODE` toggle changes the interpretation of subsequent `JUMP`s into `SEQUIN_EJECT`s at the jump destination [Source: pyembroidery README / issue discussion](https://github.com/EmbroidePy/pyembroidery).

## EXP (Melco) — detail

- **No header at all** — the file is pure stitch data [Source: search-aggregated EXP summaries, e.g. StitchPilot EXP guide](https://stitchpilot.ai/formats/exp).
- Coordinates are **relative** to the previous point, encoded as signed (2's complement) 8-bit bytes for X and Y, giving a per-axis range of -127..127 in 0.1 mm units — i.e. a **hard max single-stitch delta of ~12.7 mm**, consistent with Wilcom's documented "binary coding system: 12.7 mm — e.g. Barudan machines" [Source: Wilcom Stitch & jump length settings](https://docs.wilcom.com/embroiderystudio/26/en/OnlineHelp/Setup/machines/Stitch_jump_length_settings.htm).
- **No standardized color palette block** in the classic Melco-originated EXP — thread order/color intent has to be tracked and documented outside the file. Some Bernina-flavored EXP variants reportedly do carry basic color-scheme info, but this is not a universal guarantee across all EXP producers [Source: search-aggregated EXP summaries].

## JEF / JEF+ (Janome) — detail

- File layout (from a byte-level reverse-engineering write-up): **116-byte file header** → thread-color list → thread-type list → [JEF+ plus-header] → stitch list → {JEF+ plus-detail, JEF+ only} [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- Header fields documented include: stitch offset (bytes 0–3, little-endian), date `YYYYMMDD` (bytes 8–15), time `HHMMSSxx` (bytes 16–23), thread/color-change count (24–27), stitch count (28–31), a **hoop code** (32–35, values 0–4 mapping to specific hoop sizes), and five extent (bounding box) measurement sets in 0.1 mm units (36–112) [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- Thread colors reference a **fixed built-in palette of 78 entries**, each a 4-byte code mapping to an RGB value and a standard name [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- Stitches: signed 8-bit X/Y displacement bytes, range -127..127, 0.1 mm units. The byte `0x80` is reserved as an **escape code**: `0x80` followed by a command byte (and for most commands two more displacement bytes) introduces color change (code 1), a move instruction (code 2), or end-of-design (code 16, encoded as the 2-byte sequence `0x80 0x10` rather than the general 4-byte pattern) [Source: KDE Wiki — Janome Embroidery Format](https://community.kde.org/Projects/Liberty/File_Formats/Janome_Embroidery_Format).
- The header's hoop-size field means a JEF file can natively assert "this design needs at least hoop size N," which a validating pipeline can check against a target machine's hoop inventory before dispatch [Source: Janome — Saving Files for Janome Embroidery Machines](https://www.janome.com.au/saving-files-for-janome-embroidery-machines/).

## VP3 (Husqvarna Viking / Pfaff) — detail

- Marketed and documented (by vendors, not an independent spec) as a block-structured format: file header (design name, stitch count, dimensions), thread color info, stitch data + machine instructions, hoop positioning/layout data, and an embedded preview image [Source: aggregated vendor descriptions, e.g. embdesigntube VP3 guide](https://embdesigntube.com/en-gb/blog/vp3-embroidery-files-husqvarna-format-guide).
- Frequently described in vendor marketing as "vector-based," implying it stores more structure than a flat relative-delta stitch list, though no independently reverse-engineered byte-level spec was found in this research pass — treat the "vector" framing as a design/marketing claim, not a verified bit layout <!-- TBD: verify — no independent byte-level VP3 spec found -->.
- pyembroidery both reads and writes `.vp3`, which is the most reliable practical confirmation that its structure is well-enough understood for production tooling [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).

## HUS (Husqvarna Viking, legacy) — detail

- Predates VP3; used through the 1990s [Source: aggregated search, e.g. emblibrary Husqvarna formats help](https://www.emblibrary.com/EL/help.aspx?page=helpformathusqvarna).
- Uses a **proprietary LZSS-family compression** scheme (licensed technology related to the ARJ compressor lineage), which is a major reason it's one of the harder legacy formats for open tooling to fully round-trip [Source: aggregated search results citing Greenleaf/ARJ lineage; see also Just Solve the File Format Problem: HUS](http://justsolve.archiveteam.org/wiki/HUS).
- Files begin with one of a small set of fixed magic numbers in the first 4 bytes (`5BAFC800`, `5BFFC800`, or `5DFCC800`) [Source: aggregated search results, cross-referenced against Just Solve the File Format Problem: HUS](http://justsolve.archiveteam.org/wiki/HUS).
- pyembroidery lists `.hus` as **read-only**, i.e. it is not considered safe/complete enough to write [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery).

## PES / PEC (Brother) — detail

- A `.pes` file is a **two-layer container**: an outer PES section aimed at Brother's PE-Design authoring software, and a nested **PEC block** that is what the physical embroidery machine actually consumes (design name, color list, machine commands, low-res stitch graphic) [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).
- Versioned: headers observed from `#PES0001` through at least `#PES0060`; **the header layout differs per version**, so a parser must branch on the version string before trusting field offsets [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).
- Color handling changed generationally: **PES v1–v4 use a fixed, predefined 64-thread PEC palette** (colors referenced by index only); **PES v5/v6 replace this with configurable/custom thread definitions** [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).
- V4–V6 (and later) add an **addendum block** after the classic PEC graphics block, with ~0x90 (144) bytes of extra per-color metadata [Source: libpes wiki — PES format](https://github.com/frno7/libpes/wiki/PES-format).

## Sequins in newer formats

DST is the only format the pyembroidery project treats as natively, fully sequin-capable (`SEQUIN_MODE` / `SEQUIN_EJECT`); for other formats the encoder falls back to a configurable "sequin contingency" — converting a sequin instruction into a `JUMP`, a `STITCH`, removing it, or a format-specific "utilize" behavior [Source: pyembroidery README](https://github.com/EmbroidePy/pyembroidery). Tajima introduced the first commercial sequin embroidery machine in 1986 [Source: Wikipedia — Machine embroidery](https://en.wikipedia.org/wiki/Machine_embroidery).
